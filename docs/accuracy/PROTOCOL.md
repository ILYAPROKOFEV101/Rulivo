# Испытания точности Rulivo

Этап 1 из ACCURACY_PLAN.md: измерить исходную погрешность до изменения алгоритма. Текущий вариант журнала — `baseline_hit_test_v1`: выбор поверхности, установка по свежему hit-test и независимые якоря сохранены. Наличие журнала и зелёных тестов не подтверждает точность.

## Диагностический запуск

Журнал включается явно в debug-сборке. Обычный запуск и release его не включают. Все команды выполняются из корня проекта. `DEVICE` — серийный номер нужного телефона из `adb devices -l`; всегда выбирайте его явно, особенно при работающем эмуляторе.

```sh
./gradlew :app:assembleDebug
adb -s DEVICE install -r app/build/outputs/apk/debug/app-debug.apk
adb -s DEVICE shell am start -S -n com.ilya.rulivo/.MainActivity --ez accuracy_diagnostics true
```

`-S` завершает текущий процесс и удаляет из памяти текущую AR-сцену; экспортируйте предыдущие результаты заранее. Новая сессия создаёт отдельный файл и UUID. Для нескольких замеров в одной сессии используйте обычную очистку сцены. Счётчик ID завершённых измерений монотонный в рамках этой сессии и не обнуляется при очистке.

Добавьте каталог `platform-tools` установленного Android SDK в `PATH`, чтобы команда `adb` была доступна в терминале. Подключённый на момент разработки аппарат — Pixel 9 Pro XL; это не означает, что его точность уже проверена.

После серии сверните приложение, подождите секунду для сброса очереди и выгрузите журнал:

```sh
python3 tools/accuracy/export.py --adb adb \
  --serial DEVICE --out build/accuracy/pilot-01/logs
```

Экспорт не меняет телефон. `inventory.json` показывает UUID сессий, ID и время завершённых замеров. `export.json` содержит SHA-256 журналов и установленного APK. Храните APK и копию исходников вместе с экспериментом; проверка хеша при экспорте относится к установленной сейчас сборке, поэтому экспортируйте **до** переустановки. Один и тот же журнал из нескольких экспортов нельзя считать разными сессиями.

Журналы находятся в приватном `no_backup/accuracy/`, не участвуют в резервном копировании Android и не содержат изображения камеры, аудио, геолокацию или серийный номер аппарата. В них есть модель, версия ARCore, временные метки, пространственные координаты и результаты. Хранится до пяти сессий по 8 MiB плюс короткий конечный маркер. Экспортируйте каждую серию до ротации. Переполнение очереди, ограничение размера и отсутствие конца файла отмечаются в отчёте. При ошибке диска измерение продолжает работать, но полноценность диагностики не гарантируется; причина доступна в logcat с тегом `RulivoDiagnostics`.

Чтобы выключить запись, запустите новую сессию без extra:

```sh
adb -s DEVICE shell am start -S -n com.ilya.rulivo/.MainActivity
```

## Физические сценарии

Разметьте оба конца каждого эталона, измерьте их рулеткой/проверенным инструментом и запишите погрешность эталона. Не используйте размер из AR как эталон. Условия и допустимые границы доработки фиксируют до итоговой проверки.

| Сценарий | Эталон | Отдельно изменяемый параметр | Назначение |
|---|---|---|---|
| Матовая неподвижная поверхность | 20, 50, 100, 200 см | Дистанция камеры: например 50, 100, 200 см | Основная исходная ошибка |
| Комната / стена | 300–500 см | Положение камеры относительно концов | Длинные отрезки |
| Книга на столе | Измеренная длина и толщина | Расстояние и ракурс | Попадание на стол вместо книги |
| Край полки | Измеренный отрезок | Ракурс и фон за краем | Смена поверхности |
| Предмет перед стеной | Измеренный отрезок и зазор до стены | Ракурс и дистанция | Попадание на фон |
| Стекло, зеркало, блестящий/движущийся предмет | Отдельные эталоны | Отдельные условия | `support=unsupported`, вне заявлений точности |

Для начала: 10 попыток на каждое выбранное сочетание условий, в нескольких новых AR-сессиях. Не исключайте неуспешные попытки. Итог: минимум 30 повторений на сценарий на новой выборке и в нескольких сессиях; редкие большие ошибки требуют большей выборки. До общих заявлений подключите второй аппарат, желательно с другими возможностями Depth. `camera_distance_cm` — заранее выбранная фактическая/номинальная дистанция камеры, отдельно от `reference_cm` — длины эталона. Не заменяйте первую расстоянием из hit-test, если проверяете влияние реальной дистанции.

Для каждой попытки:

1. Заранее назначьте `trial_id`, сценарий и лимит ожидания. Измерьте/запишите освещение, материал и расположение. Секундомер/наблюдатель измеряет время от начала наведения каждой точки до подтверждения; журнал не может знать намерение пользователя начать попытку.
2. Поставьте начало и конец. Сохраните все попытки, включая отказ найти поверхность и прерывание по времени. После завершения не удаляйте линию минимум 31 секунду; осмотрите её с разных позиций, сохраняя обычные условия tracking.
3. Свяжите успешный замер с `session_id` и `measurement_id` из `inventory.json`. Журнал хранит результат подтверждения, а также последующие текущие координаты и длину. Каждая пара сессия/измерение учитывается только один раз.
4. Заполните копию `docs/accuracy/trials.csv`. Пустой шаблон намеренно не содержит фиктивных физических результатов.

Значения CSV:

- `cohort`: `pilot` для настройки или `validation` для независимой итоговой выборки.
- `algorithm`: точно из журнала, сейчас `baseline_hit_test_v1`; новые режимы будут отдельными вариантами.
- `support`: `candidate` для проверяемого сценария либо `unsupported` для отдельной группы ограничений.
- `model`, `depth_mode`, `session_id`: из журнала; несовпадение отклоняется. Для отказа до создания AR-сессии `session_id` пуст, остальные условия заполняются вручную.
- `reference_cm`, `reference_uncertainty_cm`, `camera_distance_cm`: сантиметры, десятичная точка. Эталон и дистанция положительные; погрешность эталона неотрицательная.
- `status`: `success`, `refused` или `aborted`. Успех требует `measurement_id`; отказ/прерывание требуют `failure_reason` и пустого ID. Отсутствие результата не записывается как нулевая длина.
- `point1_time_s`, `point2_time_s`, `attempt_time_s`: секунды, в том числе затраченное ожидание при отказе. Неизвестное значение оставляется пустым и получает предупреждение о пропуске. `attempt_time_s` заканчивается подтверждением/отказом и не включает последующее ожидание дрейфа.
- `lighting`, `surface`, `scenario`: одинаковые метки для одинаковых условий. `notes`: промах по фону, пауза, изменение света, дополнительные сведения об эталоне.

## Отчёт и переход к следующей итерации

```sh
python3 tools/accuracy/report.py --logs build/accuracy/pilot-01/logs \
  --trials build/accuracy/pilot-01/trials.csv --out build/accuracy/pilot-01/report
python3 -m unittest discover -s tools/accuracy/tests -v
```

Получаются `report.md`, `report.json` и `trials.csv` с результатами каждой попытки. Группировка разделяет алгоритм, аппарат, Depth, сценарий, поддержку, эталон и его погрешность, дистанцию, освещение, материал и выборку. Неподдерживаемые случаи остаются отдельными строками.

Отчёт содержит абсолютную ошибку и модуль относительной ошибки каждой успешной попытки, среднюю знаковую ошибку (систематическое смещение), медиану и p95, долю успеха, отказы/прерывания, задержки и дрейф. Модуль вычисляется до усреднения; погрешность эталона указывается отдельно, не вычитается из ошибок приложения. До/после сравниваются только группы с одинаковыми условиями. Снижение медианы вдвое само по себе не открывает следующий этап: нужны снижение крупных ошибок и приемлемые задержка и доля успеха. Их допустимые значения и абсолютный допуск в сантиметрах пока не назначены.

Окна дрейфа — первый новый кадр в [10, 11] и [30, 31] секунд после подтверждения. Если в нём tracking отсутствует, кадра нет или измерение удалено, значение остаётся неизвестным. Застывший кадр не считается новым. Позднее восстановление не скрывает потерю наблюдения. Число доступных наблюдений всегда рядом со статистикой.

Разрешение датчика и времена кадров имеют отдельную шкалу: `frame_timestamp_ns` нельзя напрямую вычитать из `observed_elapsed_ns`. Используются интервалы внутри одной шкалы. [ARCore Frame.getTimestamp](https://developers.google.com/ar/reference/java/com/google/ar/core/Frame#getTimestamp()) описывает время получения изображения; повторные `Session.update()` могут вернуть тот же кадр. Журнал отдельно считает новые, повторные и некорректные метки, пишет CPU-время обработки кадра и создания снимка диагностики. Это не время GPU и не полная задержка камеры. Чтобы оценить влияние записи, сравните одинаковые серии с включённой и выключенной диагностикой/системным профилированием.

Мировые позы между кадрами могут уточняться ARCore. Снимки включают координаты попадания относительно текущей плоскости и конца относительно начала. Нельзя считать изменение старых мировых координат самостоятельной оценкой физической ошибки.

Сейчас физической таблицы «до/после» нет. Следующий переход из плана требует исходных физических замеров; пороги устойчивости и допуски нельзя выбирать по этим unit-тестам. После пилота определяются причины промахов, критерии задержки/доли успеха, затем вводятся и сравниваются PointStabilityTracker, Raw Depth и остальные этапы.
